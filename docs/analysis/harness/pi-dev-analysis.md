# Pi-dev Sandbox: features and how they’re controlled

**As of October 28, 2026**, Pi-dev (the Pi terminal coding agent) does not ship a built-in operating-system sandbox or general-purpose permission prompt for each tool call. Its built-in tools and extensions run with the permissions of the Pi process. Pi's security page also treats prompt injection, the lack of a sandbox and user-installed extension behaviour as out of scope for security reports unless they show a privilege-boundary bypass. Safety therefore comes from two separate mechanisms: Pi’s native **project trust** gate for loading project-supplied resources, and an externally configured isolation boundary for limiting what running code can access. [Pi security](https://pi.dev/docs/latest/security) · [Pi isolated environments](https://pi.dev/docs/latest/containerization)

This distinction matters when comparing Pi with Codex and Claude Code in this folder: those products integrate command sandboxing into the agent workflow. Pi keeps the core small and lets users select external isolation or install extensions. An extension can add workflow permissions, but it is third-party code running in Pi and is not itself a protected OS boundary unless it invokes one.

## What is included in core Pi

| Capability | What it does | What it does not do |
|---|---|---|
| **Built-in tools** | Read, write, edit, search, list, and run shell commands. Commands and child processes run as the OS user that started Pi. | No filesystem jail, command allowlist, network filter, or approval prompt for every tool call. The working directory is a default location and resource-discovery root, not a restriction on accessible paths. |
| **Project trust** | Before loading most project-controlled Pi settings and executable resources, Pi asks whether the working folder should be trusted. A saved decision can be managed with `/trust`. | Does not sandbox tools, make loaded instructions safe, or prevent prompt injection. Context files such as `AGENTS.md`, `AGENTS.override.md`, and `CLAUDE.md` load independently of this trust decision unless context loading is disabled. |
| **Tool selection** | CLI `--tools` allowlists named tools; `--no-builtin-tools` removes built-ins; `--no-tools` disables all tools. | Tool selection is not a boundary against extensions or arbitrary code that already runs in Pi, and selected `bash` remains an ordinary process with Pi’s OS privileges. |
| **Extension hooks** | Extensions can observe or alter tool calls and can block a call through a `tool_call` hook. | This is an in-process policy hook, not OS-enforced isolation. Extensions have full system permissions and can execute arbitrary code. |
| **Package trust** | Project trust controls loading project-local extensions, skills, prompts, themes, system-prompt files, MCP configuration, and package declarations. | Pi packages and extensions can execute with full system access. Review their source before installing or trusting them. |

### Project-trust behavior and limits

Pi looks for protected resources including `.pi/settings.json`, `.pi/mcp.json`, `.pi/extensions`, `.pi/skills`, `.pi/prompts`, `.pi/themes`, `.pi/SYSTEM.md`, `.pi/APPEND_SYSTEM.md`, and project `.agents/skills` in the current or ancestor directories. A bare `.pi` directory by itself does not trigger a trust decision. Trusting allows project resources and settings to load; declining skips those resources. One startup caveat in the current documentation is that Pi reads the project `sessionDir` setting while selecting or creating a session, before resolving project trust.

With no CLI override, extensions can decide the `project_trust` event first; otherwise Pi applies the closest saved decision from `~/.pi/agent/trust.json`, then `defaultProjectTrust` (default: `ask`). `/trust` saves the decision. `--approve` / `--no-approve` override it for a run. In non-interactive print, JSON, and RPC modes, Pi cannot show the prompt: `ask` and `never` skip project resources, while `always` loads them. This is a resource-loading gate, not a command permission setting. [Pi security: project trust](https://pi.dev/docs/latest/security)

## Ways to isolate execution

Pi’s official guidance describes isolating either the **whole Pi process** or **selected tools**. The choice determines which processes and extensions stay outside the boundary. [Pi isolated environments](https://pi.dev/docs/latest/containerization)

| Method | Boundary and control | Main residual exposure |
|---|---|---|
| **Dedicated OS account** | Run Pi under an account with deliberately limited filesystem permissions. The OS account defines what Pi can read and change. | Pi still shares the host OS and network; anything available to that account remains in scope. [Pi security](https://pi.dev/docs/latest/security) |
| **Plain Docker** | Run Pi, built-in tools, shell commands, and extensions in a container. Mount only the task workspace; use read-only mounts where suitable. Pass credentials as environment variables or keep separate container-local state. | A read-write bind mount changes host files immediately. Passed environment variables are visible to processes. Mounting `~/.pi/agent` exposes Pi credentials, sessions, settings, and extensions. Container isolation is only as strong as its runtime and configuration. |
| **Docker Sandboxes** | Run the complete Pi process in a managed sandbox. The documented proxy can keep provider credentials on the host and substitute them for configured outbound requests. | Workspace data and permitted network destinations remain exposed. Configure provider secrets before starting; logging in inside the sandbox writes a real credential there. |
| **NVIDIA OpenShell** | Run Pi and its tools/extensions in a local or remote sandbox with filesystem, process, network, credential, and inference policies. Remote files must be cloned or explicitly uploaded/downloaded. | Resources deliberately exposed through policy or data transfer remain accessible. Inference credential handling depends on gateway routing configuration. |
| **Gondolin extension** | Keep Pi on the host but route built-in tools and user `!` commands into a local Linux micro-VM. The documented example overrides `read`, `write`, `edit`, `bash`, `grep`, `find`, and `ls`; the working folder is mounted at `/workspace`. | Pi itself and other extension tools remain on the host unless they delegate. Commands inherit the host environment, so environment-based provider keys can cross into the VM. A host mount is still writable unless configured otherwise. |

Whole-process isolation is the more complete pattern when extensions or package code are in scope. Tool-only isolation narrows exposure from the built-in tools, but does not constrain Pi itself or arbitrary host-side extension tools. In all cases, exposed files, credentials, environment variables, network services, and mounts determine the effective boundary.

### Practical controls

- **Limit filesystem exposure:** mount or copy in only task files; avoid mounting the host Pi home directory; choose read-only mounts when writes are not needed.
- **Limit credentials:** keep credentials outside the environment where possible; use short-lived and narrowly scoped tokens; treat environment variables as visible to child processes.
- **Limit network exposure:** restrict egress when commands do not need it; consider the proxy and inference path separately from general command traffic.
- **Limit loaded code:** review extensions and packages; use project trust to prevent unreviewed project extensions/settings from silently loading.
- **Limit tool availability:** use `--tools`, `--no-builtin-tools`, or `--no-tools` to remove capabilities from the model’s tool list, understanding this is not an OS sandbox.
- **Improve recovery:** use version control, snapshots, or backups; inspect changes and session contents before sharing or applying them elsewhere.

These measures address different risks. Project trust reduces automatic loading of project-controlled executable resources; tool selection reduces the agent’s available interface; OS/VM isolation restricts what a process can access after it runs. None substitutes for the others.

## Common extension-based permission options

Pi is designed to be extended, so a realistic Pi comparison should include the common safety add-ons rather than stop at the permissive core. The Pi package catalog currently lists several actively used permission/sandbox extensions. They remain third-party code, can change independently, and must be reviewed and configured; Pi itself warns that extensions execute with the process's full OS permissions. [Pi extensions](https://pi.dev/docs/latest/extensions) · [Pi package catalog](https://pi.dev/packages?name=pi-sandbox)

| Extension pattern | What it adds | Main limitation to compare |
|---|---|---|
| **pi-permission-modes** | Broadest integrated option in the catalog sources reviewed: configurable allow/ask/deny policy across bash, file tools, project resources, web search, extension tools, and skills; structural bash parsing; OS-level sandbox for bash; network allowlist prompts and session grants. Modes include Default, Plan Mode, Build, and YOLO. | Only bash is OS-sandboxed; direct file tools rely on in-process policy/backstops. YOLO disables safeguards. Windows uses a separate-account backend and is documented as alpha; unsupported/unavailable sandbox states need active checking. Windows needs a one-time `/sandbox install` with UAC and only prompts until installed; if the sandbox is unavailable, in-project bash prompts instead. Commands that leave the project run unsandboxed after approval, the macOS sandbox leaves loopback ports open, and project configs can only make modes stricter. Package/config updates and platform setup matter. [Package docs](https://pi.dev/packages/pi-permission-modes) |
| **pi-sandbox** | OS sandbox for bash using macOS sandbox-exec or Linux bubblewrap; interactive path/domain prompts; session, project, or global grants; direct read/write/edit tools are checked against filesystem policy. Catalog describes it as an OS-level sandbox with interactive prompts and the current listing shows about 5.9k downloads per month (v0.7.3). | Direct file tools are checked in-process, not OS-sandboxed. Grants saved to project/global config persist, and affected sessions may need restart to receive consistent updates. Network-disabled mode bypasses domain filtering. Review its detailed defaults and prompt semantics. [Package docs](https://pi.dev/packages/pi-sandbox) |
| **pi-ask-permission** | Approval layer across tool calls, including workspace roots, manual/accept-edits/auto modes, no-UI behavior, remembered approvals, and an optional model judge (off by default). Calls that leave the project still ask in every mode; auto mode only auto-approves inside the project. Useful when the desired control is human review of actions. | It is an approval/policy extension, not an OS sandbox. Its read-only bash check is a classifier, and its own docs recommend a sandbox when deterministic enforcement is needed. Tool allow rules may allow every command of a tool such as bash. [Package docs](https://pi.dev/packages/pi-ask-permission) |

These options are not equivalent. For a user who wants familiar prompts plus OS enforcement, `pi-permission-modes` or `pi-sandbox` combines both layers, with different tool coverage and policies. `pi-ask-permission` supplies approval workflow without independently containing code. A common hardened pattern is to pair a reviewed permission extension with whole-process Docker/OpenShell isolation when the project or extension itself is untrusted. Avoid stacking multiple policy extensions without checking hook order and whether one extension can bypass another; each extension runs with full Pi process permissions.

## Practical assessment

Pi’s security model is explicit and composable, but the baseline local experience is permissive: a model-generated shell command can act with the user’s OS permissions without Pi asking first. Project trust protects the startup resource-loading path; it does not confine execution. A strong setup for untrusted repositories or unattended work is to run the complete Pi process in a container, VM, or managed sandbox, expose only needed workspace files, keep credentials out of the guest, and restrict outbound network access. For trusted, monitored local development, a dedicated account and tight mounts/tool selection may be adequate, with the understanding that they are not equivalent to a dedicated VM boundary.

The central comparison question is therefore **which process is isolated**. With whole-process isolation, Pi, shell commands, and extensions share the guest boundary. With tool-only isolation, only explicitly delegated operations are constrained. With no external isolation, Pi and all loaded extensions share the host user’s access.
