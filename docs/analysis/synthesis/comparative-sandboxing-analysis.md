# Coding-agent harnesses and execution sandboxes: a layered comparison

This comparison synthesizes the workspace notes on Pi-dev, Claude Code, Codex, Docker, E2B, and NVIDIA OpenShell. It separates **agent harnesses** (which run the model and expose tools) from **execution environments and policy runtimes** (which contain an agent or its code). They operate at different layers and can be combined; they are not interchangeable products. This is not a product security certification. Verify details against the versions and policies actually deployed.

## The two layers

- **Harness layer — Codex, Claude Code, Pi-dev.** Compare which tools and commands the agent can invoke, how approvals work, what native filesystem/network controls exist, and what stays outside those controls. Codex and Claude Code include command sandboxing; Pi-dev core does not.
- **Execution layer — ordinary Docker, Docker Sandboxes (`sbx`), E2B, NVIDIA OpenShell.** Compare the boundary around processes or workloads, workspace sharing and handoff, network and credential policy, lifecycle, and operational fit. These can run an agent process or user code; integration determines what is actually inside.

The key coverage question is: **is the complete agent process inside the boundary, or only selected commands/tools it launches?** A strong outer boundary cannot control host-side connectors that remain outside it, and an inner harness sandbox cannot grant access denied by the outer runtime.

## Executive summary

These options sit at different layers and should not be treated as interchangeable:

- **Codex and Claude Code sandboxes** are local command-execution boundaries integrated into their agents. They are convenient for normal coding, but cover shell processes rather than every connected tool or service.
- **Ordinary Docker containers** primarily package environments and constrain processes/resources. They share the host kernel, and mounts or daemon access can expose the host.
- **Docker Sandboxes (`sbx`)** put each local agent in a lightweight microVM with its own Linux kernel, separated from host processes, filesystem (except explicit shares), network, and Docker daemon. Ordinary containers share the host kernel. `sbx` also gives the agent a private Docker Engine and workspace handoff modes.
- **E2B’s primary offering** is an API-driven sandbox service for cloud execution, and its open-source repository documents self-hosting the runtime on supported infrastructure. Separately, a third-party “E2B Local Sandbox Guide” describes a local, E2B-SDK-compatible control plane using Docker containers or Shuru microVMs on macOS. That is a compatibility implementation/guide, not evidence that the standard hosted E2B service itself runs locally. The Docker backend retains ordinary container’s shared-kernel caveat; Shuru is described as a microVM option.
- **NVIDIA OpenShell** is a policy-oriented runtime/control plane: it combines sandbox drivers with path, process, network, credential, and middleware controls, including dynamic network policy.
- **Pi-dev** has no native command sandbox or per-tool approval system. Native project trust controls which project resources load; isolation is supplied by an external runtime or an extension. Official examples include whole-process Docker, Docker Sandboxes, OpenShell, and tool-only Gondolin. Optional packages can add approval and sandbox behavior, but are not Pi core.

For routine local work, an agent-native workspace boundary is the least operationally heavy choice. For untrusted autonomous code, a VM/microVM boundary with deliberate data transfer is a stronger default. For a product that creates many remote execution environments, E2B or OpenShell may fit better, depending on how much policy and fleet control the application needs.

## E2B local compatibility and deployment

The E2B repository describes E2B as open-source infrastructure for running generated code in isolated sandboxes **in the cloud**, controlled with the E2B JavaScript or Python SDK. It also has a self-hosting path: its README points to an Embed deployment guide and lists AWS, GCP, Azure, and general Linux machines. This means E2B is not limited to E2B-operated cloud, but the documented self-hosting route is infrastructure deployment, not simply running the normal E2B service as a local desktop sandbox. ([E2B repository](https://github.com/e2b-dev/e2b))

The linked [E2B Local Sandbox Guide](https://mcpmarket.com/tools/skills/e2b-local-sandbox-guide) is a third-party listing, attributed to a community author. It describes a local control plane that mirrors the E2B API so the standard E2B SDK can target local sandboxes, with Docker-container and Shuru-microVM backends. The listing says Shuru is for macOS. This can support local development and E2B-compatible workflows, but it should be evaluated as a separate implementation: SDK compatibility does not mean it is the official E2B hosted runtime or that it shares all of E2B’s security properties. In particular, the Docker backend is still a container boundary and shares the host kernel; the listing does not provide enough detail to independently assess its isolation or maintenance.

## What matters most in practice

### Docker Sandbox costs and approvals

Docker's `sbx` CLI and local sandbox compute are free, including commercial use. Cloud sandbox compute is pay-as-you-go, and model-provider charges are separate. Docker AI Governance is a separate paid, per-license plan for centralized organization policy, audit, and sign-in enforcement. [Docker Sandboxes FAQ](https://docs.docker.com/ai/sandboxes/faq/), [AI Governance plan](https://docs.docker.com/subscription-billing/plans/ai-governance/)

Approval behavior is narrower than a general agent permission escalation: a local or organization network approval grants the exact destination (or HTTP method/path) for subsequent requests from that sandbox; the blocked attempt must be retried. An MCP `@requireApproval` policy prompts in the connected client and, if approved, permits that one governed call. It does not establish a persistent grant or out-of-band admin approval queue. The Docker Home UI manages governance policies and audit events; pending network approvals use `sbx policy approval`, and MCP confirmation is delivered through the MCP client. [Network approvals](https://docs.docker.com/ai/sandboxes/governance/access-controls/network/), [MCP approval](https://docs.docker.com/ai/sandboxes/governance/access-controls/mcp/), [organization policies](https://docs.docker.com/ai/sandboxes/governance/access-controls/organization/)

#### Differences that prevent a simplistic feature count

- **Filesystem policy is aimed at different resources.** Docker AI Governance governs which host paths may be mounted as a sandbox workspace, with read/write mode. OpenShell Landlock governs paths visible to sandbox processes. Compare host exposure and in-guest visibility separately.
- **Request inspection differs.** Docker organization network policies can constrain destination and HTTP method/path; its MCP Cedar policy governs operations through the Docker MCP gateway. OpenShell can bind network reach to a binary and destination, then inspect supported protocol requests; APF adds Cedar decisions/effects only for traffic routed through its middleware. Neither product should be credited with governing direct host-side tools or traffic that bypasses its enforcement path.
- **Governance provenance differs.** Docker AI Governance is a vendor-hosted organization policy plane with Docker Home, team scopes and sync. OpenShell alone uses gateway policy and identity. APF adds signed bundle verification and provenance, but its reviewed documentation is Dev/currently version-sensitive and it adds self-hosted services and a protected signing pipeline.
- **A custom UI is not an enforcement layer.** For Docker, a UI over local `sbx policy` commands cannot override active org policy; the official org Governance API is the paid route. For OpenShell, a UI can call gateway APIs, but with APF enabled its policy write path must become bundle authoring/review/sign/publish. In either case, identity enforcement and device/runtime protection determine whether the policy plane is authoritative.

#### Proof-of-concept questions before choosing

1. Pin the exact Docker Sandboxes, OpenShell, and APF versions. On the same host, test `sbx` microVM against OpenShell Docker driver and OpenShell MicroVM driver; compare Kubernetes separately as a remote cluster deployment.
2. Apply semantically matched policies: workspace mount/write; read/write within the guest; egress to one allowed and one denied host; HTTP read versus write; MCP read/write; and credential use. Record gaps where a feature has no equivalent.
3. Exercise approval paths: who sees the prompt, who can answer, scope/duration of the grant, whether retry is required, what happens with a hard deny, and what is logged. For OpenShell/APF, include Policy Advisor, signed-bundle update, and external PIP approval rather than treating those as one flow.
4. Measure cold start, pause/resume, package install/build/test speed, CPU/memory/disk use, network overhead, and costs. Separate local host cost from Docker cloud compute and from self-hosted cloud/Kubernetes infrastructure.
5. Test policy freshness, control-plane outage, offline workstation, user without a Governance license, personal-account sign-in, gateway restart, and audit delivery failure. Verify whether each system fails open, fails closed, or retains its last valid policy.
6. Threat-model the management UI independently: SSO and role separation, gateway credentials, bundle signing, CSRF, audit immutability, concurrent policy changes, and what a compromised UI/backend could alter.

### Building a permissions Web UI for OpenShell/APF

An OpenShell-only UI can use the gateway SDK/API to inventory sandboxes, inspect base and effective policies, review denials and pending network proposals, and apply or approve dynamic network changes. Filesystem and process changes still require sandbox recreation. In an APF-governed deployment, direct policy edits and OpenShell draft approvals are refused; the UI must manage reviewed, validated, higher-revision signed bundles and observe their publication and activation. Per-action approval requires an external approval service whose decision APF can read as a Policy Information Provider fact. In both modes, put gateway credentials and APF signing keys behind a backend, enforce SSO/role/workspace authorization, show diffs and impact, and keep an audit trail. ([OpenShell policy API workflow](https://docs.nvidia.com/openshell/latest/how-it-works/policies/manage-policies), [APF integration limits](https://docs.nvidia.com/agent-policy-fabric/security/enforcement-coverage-and-limitations), [APF providers](https://docs.nvidia.com/agent-policy-fabric/integrations/policy-information-providers), [OpenShell OIDC](https://docs.nvidia.com/openshell/latest/how-it-works/gateways/authentication))

### MCP policy scope in OpenShell and APF

OpenShell’s MCP controls are endpoint rules inside the sandbox’s network policy: they scope MCP methods and tool names by binary and remote server for inspected Streamable HTTP egress. They do not form a standalone MCP server registry, do not match tool arguments, and do not cover local stdio MCP servers or server-to-client MCP messages. APF capability grants add a separate Cedar authorization layer for routed MCP `tools/call` requests; they require an explicit grant and can constrain arguments. With APF, the grants are delivered in signed bundles, while OpenShell still controls which destinations the sandbox can reach. ([OpenShell MCP policy](https://docs.nvidia.com/openshell/latest/how-it-works/policies/schema), [APF capability grants](https://docs.nvidia.com/agent-policy-fabric/author-policies/capability-grants), [APF compatibility](https://docs.nvidia.com/agent-policy-fabric/about/support-and-compatibility))

### 1. Isolation strength is only one axis

A shared-kernel container, an OS command sandbox, and a microVM do not offer the same boundary. The local Codex and Claude controls are integrated and useful for limiting ordinary command access, but their documented scope is narrower than a VM boundary. Ordinary Docker is also not equivalent to a VM: it shares the host kernel. Docker Sandboxes and E2B use microVMs, while OpenShell's effective boundary depends in part on the selected compute driver.

Pi makes the distinction especially visible: the agent framework itself supplies no execution boundary, but official containerization guidance lets operators choose whole-process isolation or tool-only routing. This does not make stronger isolation automatically safer in every deployment. A microVM with a read-write host share, broad egress, forwarded identity, or exposed service can still create significant paths across the boundary.

### 2. Data paths often dominate the residual risk

The main paths from an agent environment to sensitive systems are:

- **Workspace mounts and staged files:** direct mounts make edits immediate; clone mode prevents writes through the source mount but still exposes repository contents, including ignored files and secrets left inside it.
- **Network egress:** broad allowlists can become exfiltration routes. Pi core has no command-network filter; an external runtime or optional extension must supply it. E2B defaults outbound access on; Codex workspace-write defaults command networking off; OpenShell denies outbound traffic unless policy grants it. Docker `sbx` uses presets, so the effective rules should be inspected.
- **Credentials and identity:** proxy-injected credentials reduce raw-secret exposure, but the agent can still use an authorized credential against its permitted destination. Forwarded SSH agents let code authenticate or sign even when the private key is not readable.
- **Host integrations:** MCP servers, plugins, browser/computer-use tools, local proxies, and app connectors may have permissions outside the shell or guest boundary.
- **Returned artifacts:** scripts, hooks, CI files, IDE tasks, and generated code can execute later on the host. Review outputs before triggering them.

### 3. Approval prompts and sandboxing solve different problems

Codex and Claude both distinguish whether an action may run from what it can access once run. Approval policies reduce unauthorized action; the sandbox limits impact. An approval-free workflow can still retain a sandbox, and a sandbox does not make every action safe. Pi core has project-trust prompts, but these only decide whether project configuration/resources load; they do not approve commands or tool calls. Pi extensions can implement tool approval, and external runtimes can enforce process boundaries, but those are separate, optional controls. Similar separation applies to Docker/E2B/OpenShell: orchestration permissions and runtime isolation are different control layers.

### 4. Network policy ranges from broad to request-aware

Codex and Claude can constrain command traffic through proxies, but only traffic routed through those proxies is governed there. Pi core has no network-policy surface; when Pi runs in Docker, network settings are external, while Docker Sandboxes, OpenShell, Gondolin, or optional permission extensions provide different network controls. Docker Sandboxes offers destination policies and network presets. E2B offers destination filtering but has documented protocol and port limits. OpenShell has the most detailed request-level policy in these notes, including method/path and selected API-protocol controls, plus audit/enforce modes and middleware. More expressive policy also adds configuration complexity and a need to verify the *effective* policy.

### 5. Persistence changes the threat model

Local sandboxes generally operate on a live workspace unless configured otherwise. Docker Sandboxes can persist an environment or isolate changes in clone mode. E2B can pause/resume full machine state or snapshot it, so secrets and processes may persist. OpenShell has lifecycle and policy controls, but filesystem/process changes generally require sandbox recreation while network rules can be updated live. Treat snapshots, persistent disks, and mounted volumes as sensitive data.

## Recommendations by scenario

| Scenario | Good starting point | Key configuration choice |
|---|---|---|
| Familiar agent, ordinary local development | Codex or Claude native sandbox | Keep the filesystem boundary narrow; enable only needed command network access; understand which tools run outside it. |
| Pi-dev on a trusted local repository | Pi core with a least-privilege account, or Pi plus a reviewed permission extension | Remember that project trust is a resource-loading gate, not execution isolation; set external limits for files and network if needed. |
| Pi-dev on an untrusted repository or unattended job | Run the complete Pi process in Docker Sandboxes or OpenShell | Do not expose the host Pi home or broad credentials; restrict egress and workspace mounts. Gondolin is tool-only, so audit all host-side extensions. |
| Untrusted agent or autonomous code that can install/run services | Docker Sandboxes or another microVM runtime | Prefer clone or mountless mode, restrict egress, avoid SSH forwarding and broad host integrations, review outputs before host execution. |
| Repeatable build/test job with trusted inputs | Ordinary Docker may suffice | Non-root user, minimal mounts/capabilities, resource limits, explicit egress design, and no host daemon socket. Use a VM boundary if code is untrusted. |
| Product feature that runs user code remotely | E2B | Disable or narrow egress as appropriate; token-gate ingress; keep platform credentials outside guest env; set timeouts and explicitly clean up persisted sandboxes. |
| Centrally governed agent fleet with detailed network/credential policy | NVIDIA OpenShell | Pin runtime/driver choices, use hard filesystem enforcement where required, inspect effective policy and provider bindings, centralize identity and logs. |

## Overall assessment

There is no single winner because the products solve different problems. **Codex and Claude optimize for local developer workflow; Pi-dev for an extensible, composable agent core; ordinary Docker for packaging and resource control; Docker Sandboxes for local autonomous-agent isolation; E2B for managed remote execution; OpenShell for policy-driven operations.** Pi requires the operator to choose and verify more of the security boundary, while its official containerization paths allow it to use the same external runtimes compared here.

The most useful comparison question is therefore not simply “which sandbox is strongest?” It is: *what code is inside the boundary, what data can it read, where can it send data, what identities can it use, and how are results brought back?* On those dimensions, a tightly configured weaker boundary can be safer than a powerful microVM with broad mounts and network access, while a microVM is the preferable starting point for genuinely untrusted autonomous execution.
