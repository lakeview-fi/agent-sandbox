# Requesting additional access during a coding-agent task

This note compares what happens when an agent needs a file path or network destination that was not allowed when its task started. It distinguishes three things that are easy to conflate:

1. **The agent asks for access** through an approval or policy-proposal flow.
2. **A user/operator changes policy** while the task is running.
3. **The sandbox actually applies the changed boundary** without restarting the workload.

Approval of one command is not always the same as granting lasting access to a path or destination. Details depend on the product, platform, and configured permission mode.

## Quick reference across both layers

This is a cross-layer index, not a like-for-like product ranking. Codex, Claude Code, and Pi-dev are harnesses: focus on agent prompts, approvals, and grants. Docker, Docker Sandboxes, E2B, and OpenShell are execution environments or policy runtimes: focus on operator policy changes and whether a running workload receives them. A harness approval does not necessarily alter the outer runtime policy.

## Harness request and approval flows

### Codex

Codex separates the sandbox boundary from the approval policy. A command that stays inside the boundary can run without a prompt under common settings; an action that needs more access can trigger an approval. A reviewer may authorize the action or change the active permissions. Treat approval of one command as authorization for that command unless the UI/configuration explicitly says it changed the ongoing policy. Codex's writable roots and network settings are durable policy controls, separate from a one-time approval. ([Sandbox documentation](https://learn.chatgpt.com/docs/sandboxing), [Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security))

### Claude Code

Claude Code has both command permission checks and an OS-enforced sandbox for shell processes. The `/sandbox` controls, filesystem rules, network rules, and managed settings determine which requests can be approved or denied. A permission prompt should not be confused with a filesystem or network rule being permanently added. Managed strict policies can prevent a local/session-level widening. The sandbox remains scoped to shell execution; other tools have separate controls. ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing))

## Execution-runtime policy changes

The following products govern the outer execution boundary. They do not describe a harness deciding whether an agent may invoke a tool.

### Ordinary Docker

An ordinary container has no standard agent-specific broker that asks a human to approve a new path or URL and then updates the container. The operator configures mounts, capabilities, and network externally. A running container may be able to reach a service already available on its network, but granting new host filesystem access generally requires changing the container setup and often recreating it.

### Docker Sandboxes (`sbx`)

`sbx` exposes operator-managed network rules. A rule can be added while a sandbox runs and applies immediately. Without organization governance, an unmatched request is blocked and can be approved by the developer through `sbx policy approval`, creating a per-sandbox grant for that destination; the agent retries. Workspace sharing is a separate setup choice: mountless, direct read/write, or clone mode. A new host path is not implicitly exposed just because the agent asks for it. Keep host file access narrow and use clone mode when the agent should work on a private copy. ([Local policy](https://docs.docker.com/ai/sandboxes/security/policy/), [Isolation layers](https://docs.docker.com/ai/sandboxes/security/isolation/))

### E2B

E2B provides SDK/API controls for sandbox files, volumes, templates, and networking. The workspace analyses describe egress rules as sandbox configuration and do not document an interactive agent approval workflow for a blocked destination or general live expansion of host file mounts. For a concrete deployment, verify the E2B SDK/API version and the exact update behavior before relying on a policy change to affect an already-running sandbox. The third-party local E2B-compatible guide is a separate implementation and should not be assumed to have E2B's control-plane behavior.

### NVIDIA OpenShell

OpenShell has the clearest explicit **agent request → operator review → live network update** flow. Policy Advisor lets the agent submit a scoped network proposal after denial; the agent cannot approve its own request by default. The approved rule takes effect in the running sandbox. Filesystem and process settings are different: they are startup controls, and filesystem changes require sandbox recreation. ([Policy Advisor](https://docs.nvidia.com/openshell/dev/how-it-works/policies/advisor), [Manage Policies](https://docs.nvidia.com/openshell/dev/how-it-works/policies/manage-policies))

## Pi-dev harness notes

Pi core's `/trust` and `--approve` / `--no-approve` concern project-resource loading only. They are not dynamic filesystem or network grants, and there is no built-in prompt when a shell command wants another path or host. Pi's official containerization guidance instead puts policy changes at the external boundary: change the container, VM, or gateway configuration, and use that runtime's documented update/restart semantics. Tool-only Gondolin routes selected built-in tools but leaves Pi and non-delegating extensions outside the VM.

Optional packages change this answer. `pi-permission-modes` advertises prompts for out-of-project paths and hosts, session grants/denials, and live network filtering toggles; `pi-sandbox` has path/domain prompts with session/project/global grants; `pi-ask-permission` adds tool approval but not an OS boundary. These are extension-specific controls, not Pi-core guarantees or general host-mount hot-add mechanisms. Review package source, active mode, and actual sandbox status before relying on them. ([Pi security](https://pi.dev/docs/latest/security), [Pi containerization](https://pi.dev/docs/latest/containerization), [Pi permission-modes](https://pi.dev/packages/pi-permission-modes), [pi-sandbox](https://pi.dev/packages/pi-sandbox), [pi-ask-permission](https://pi.dev/packages/pi-ask-permission))

## Practical takeaway

If access needs to expand during work, **OpenShell provides the clearest runtime-native, operator-reviewed network proposal and live update**. **Docker Sandboxes provides operator-managed live network rule changes**. Codex and Claude provide agent-integrated approval mechanisms for boundary-crossing actions. **Pi core has no access-expansion prompts; optional Pi extensions can add them, but their behavior and enforcement are package-specific.** For filesystem access, none of these mechanisms should be assumed to safely hot-add arbitrary host paths: distinguish a one-off tool approval from changing the sandbox mount. Ordinary Docker and the analyzed E2B setup rely primarily on operator/API reconfiguration rather than an agent-facing approval broker.
