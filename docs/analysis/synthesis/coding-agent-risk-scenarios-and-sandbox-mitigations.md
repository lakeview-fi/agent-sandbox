# Coding-agent risks across harness and execution layers

This report maps common risks from running a coding agent on or for a developer’s machine to the controls described in the workspace analyses. It covers the **harness layer** (Pi-dev, Codex, Claude Code) and the **execution layer** (ordinary Docker, Docker Sandboxes (`sbx`), E2B, NVIDIA OpenShell). Harness controls govern agent permissions and selected tool/command calls; execution environments govern the processes and data paths placed inside them. Apply the two views together when both layers are present.

## How to read the comparison

Sandboxing limits access paths; it does not decide whether an allowed action is wise. A sandbox may stop a command from reading a host file or reaching a service, but it generally does not understand that a SQL statement is destructive or that an API request is dangerous. The impact also depends on what is mounted, which credentials are available, and whether the agent uses a shell command or a separately connected tool.

Ratings below are qualitative, based on the documented features in the workspace notes:

- **Strong control**: a documented boundary directly blocks or substantially limits the path when configured as intended.
- **Partial control**: useful protections exist, but the outcome depends on configuration, protocol, mount, or tool coverage.
- **Little/no direct control**: prevention depends mainly on service permissions, approval policy, operator review, or a separate tool’s controls.

These are comparative descriptions, not a security certification. Real deployments can differ by platform, policy, version, and integrations.

## Risk scenarios

| Risk | Example impact | Main boundary or control needed |
|---|---|---|
| **Project-file destruction or tampering** | Delete source files; overwrite configuration; alter Git hooks, CI, build scripts, IDE tasks, or agent settings | Limit writable paths; use read-only source or a private working copy; review generated changes before running or merging them |
| **Host-file or settings access** | Read personal files, credentials, shell profiles, or alter host settings and install software | Filesystem isolation, least privilege, narrow mounts, and avoiding host administrator access |
| **Database or local-service destruction** | Drop tables, alter records, invoke an admin endpoint, or delete local data | Keep the service unreachable unless needed; use separate least-privilege credentials and disposable data; approval for commands is supplementary |
| **Credential theft or misuse** | Read `.env`, cloud keys, tokens, SSH keys, or use a forwarded agent to sign/authenticate | Keep secrets outside readable paths; proxy credentials where available; restrict credential scope and destination; disable unnecessary identity forwarding |
| **Network exfiltration or unexpected connections** | Upload source/secrets, contact attacker-controlled infrastructure, download and run code | Deny-by-default or narrowly allowlisted egress; ensure all relevant processes/protocols use enforcement; restrict DNS, UDP, and local-network paths as applicable |
| **Risky websites and downloaded content** | Follow malicious instructions, fetch compromised packages, or run downloaded scripts | Browser/tool-specific controls, package provenance, network restrictions, and review before execution; shell sandboxing may not cover browser/connector traffic |
| **External account or SaaS side effects** | Send messages, change issues, push code, alter cloud resources through an MCP server, plugin, or connector | Apply permissions and approvals at the connector/service; sandbox the connector or limit its identity; shell boundaries do not automatically cover these calls |
| **Delayed execution through generated artifacts** | A malicious hook, CI workflow, package lifecycle script, or shell startup file runs later on the host | Review diffs and fetched branches; avoid automatically executing newly written scripts; protect sensitive configuration paths |
| **Supply-chain compromise** | Install a malicious package or compromised tool that accesses files or changes build output | Pin/review dependencies, restrict install network, build in disposable environments, and keep credentials out of build contexts |
| **Resource exhaustion or cost** | Fill disk, consume CPU/memory, fork processes, or start costly cloud jobs | Enforce CPU, memory, disk, process, timeout, and concurrency limits; clean up persistent environments |
| **Persistence and stale state** | A paused sandbox retains secrets/processes, or snapshots preserve sensitive data | Define retention and cleanup; inspect snapshot/volume contents; explicitly kill or remove environments when done |

## Harness controls by risk

The first two product columns below are agent-harness controls. They describe command boundaries and agent approvals, not complete workload isolation. Pi-dev is handled in its own profile because its core has no execution sandbox; optional extensions are not core guarantees.

## Execution-boundary controls by risk

The Docker, Docker Sandboxes, E2B, and OpenShell columns describe execution environments or policy runtimes. Their controls apply only to the workload actually placed inside the boundary. Codex and Claude columns are retained in the same risk matrix as a direct reference to their narrower native command controls; do not interpret the table as a single-product ranking.

### Pi-dev mitigation profile

Pi-dev is covered separately because its core has no execution sandbox or general per-tool approval system. For a typical extended setup, the most relevant package options are `pi-permission-modes` (tool policy plus sandboxed bash), `pi-sandbox` (interactive filesystem/network policy plus sandboxed bash), and `pi-ask-permission` (approval policy without OS isolation). These are extension behaviors, not Pi-core guarantees. When the complete Pi process runs inside Docker, Docker Sandboxes, or OpenShell, the corresponding runtime column above describes that boundary. Official tool-only Gondolin routing leaves Pi and non-delegating extensions on the host.

| Risk | Pi-dev core and available control choices |
|---|---|
| **Project-file destruction/tampering** | **Little direct control in core; partial with add-ons.** `pi-permission-modes` and `pi-sandbox` gate write/edit and sandbox bash, while `pi-ask-permission` can require approval. File tools are still extension-mediated in-process; use read-only mounts or private copies for an OS-enforced boundary. |
| **Host files/settings access** | **Little direct control in core.** Pi uses the starting OS user's access; working directory is not a jail. Run under a restricted account or isolate the complete process. Tool-only Gondolin leaves Pi and non-delegated extensions on the host. |
| **Database/local-service destruction** | **Little direct control in core.** No SQL-aware guard or built-in network boundary. Use service-side least-privilege roles and keep databases unreachable unless needed. |
| **Credential theft/misuse** | **Little direct control in core or common add-ons.** Permission prompts/sandbox policies can restrict paths, but there is no native Pi credential broker. Readable files and inherited environment variables are in scope. Container env vars are visible to guest processes; Gondolin inherits host environment. OpenShell routing or Docker Sandboxes proxy substitution can protect supported inference credentials. |
| **Network exfiltration/unexpected connections** | **Little direct control in core; partial with sandbox add-ons.** `pi-permission-modes` and `pi-sandbox` advertise domain filtering and prompts for unlisted hosts, enforced for sandboxed bash; `pi-ask-permission` can ask before tool calls but does not itself filter process egress. Configure the container/VM network for a wider boundary. `PI_OFFLINE` controls Pi's own automatic network activity, not general shell networking. |
| **Risky websites/downloads** | **Little/partial.** No native egress filtering or browser isolation guarantee. Restrict the external runtime network and review package provenance; allowed sources can still serve malicious content. |
| **External account or SaaS side effects** | **Little direct control.** Project trust can gate loading project MCP configuration, but it does not limit the actions of a trusted server. Scope service identities and permissions independently. |
| **Delayed execution/artifact risk** | **Little direct control.** Generated hooks, scripts, and CI changes can execute later on the host. Whole-process isolation reduces immediate host access but does not certify returned artifacts. |
| **Supply-chain compromise** | **Little/partial.** Package installs and extensions execute with Pi's permissions. Project trust controls project package loading, not package trustworthiness; pin and review code and install/build in an isolated environment. |
| **Resource exhaustion/cost** | **Little direct control in core.** Apply container/VM CPU, memory, process, disk, timeout, and concurrency limits externally. |
| **Persistence/stale state** | **Partial by chosen runtime.** Pi sessions and its agent directory persist by configuration. Container volumes, mounts, or VM snapshots may retain credentials and state; set explicit retention and cleanup. |

## Risks the sandboxes do not eliminate

The controls below can reduce exposure, but none makes an agent safe against every consequence of an action it is allowed to take. “Does not mitigate” here means the sandbox boundary itself does not prevent the described outcome; a separate approval rule, service permission, or application control may still do so.

| Residual risk | Sandboxes with a relevant mitigation | Sandboxes that do not directly mitigate it / remaining gap |
|---|---|---|
| **Destructive SQL or API calls against an accessible service** | Codex, Claude Code, Pi with a restrictive external runtime, Docker Sandboxes, E2B, and OpenShell can restrict network or filesystem paths to services. OpenShell can inspect selected HTTP/API request types. | **All seven agent/runtime choices** lack general database-semantic protection. Pi core has no network restriction; Pi in an external runtime inherits that runtime's reachability controls. If the agent can connect and its identity can drop tables or delete records, no sandbox boundary reliably recognizes that as destructive. Use least-privilege service identities, disposable data, backups, and service-side safeguards. |
| **Harmful edits inside an intentionally writable workspace** | Codex/Claude can use read-only mode or narrower paths; Docker Sandboxes clone/mountless modes protect the host working tree; E2B/OpenShell can keep host data outside the guest or restrict paths. | **Any mode that grants the agent write access to a file** allows it to damage that file. Codex/Claude workspace-write, Docker read-write mounts and `sbx` direct mounts are intentional write paths. E2B mounted volumes and OpenShell writable work directories are also exposed to allowed writes. Review and backups are still needed. |
| **Misuse of allowed credentials** | Claude credential deny/mask; Docker Sandboxes proxy injection; E2B Secrets; OpenShell provider credential brokering can keep raw secrets out of the guest for supported flows. Filesystem policies in Codex/OpenShell can also block some secret-file reads. | **No credential feature prevents all misuse of an authorized identity.** A credential can still be used against an allowed destination, and ordinary Docker environment variables/mounts are readable to code inside the container. Proxy injection protects secret values, not the authority those credentials grant. |
| **Actions through tools outside the command sandbox** | OpenShell’s gateway/provider policy can govern some sandbox network/provider access; Docker Sandboxes has policy support for declared integrations. Whole-process Pi isolation includes extensions running in Pi; Pi's official Gondolin tool-only setup does not include other extension tools unless they delegate. | **Local command boundaries do not automatically govern other tools.** Codex/Claude web/browser, MCP, plugins, connectors, hooks, or desktop control may use separate paths. Docker Sandboxes notes that local stdio MCP servers registered with its gateway run on the host. E2B guest isolation does not constrain the application-side SDK or external integrations. Pi project trust only governs project-resource loading, not actions of trusted MCP servers. Apply separate tool and account permissions. |
| **Data disclosure in model context or service responses** | File isolation and credential controls in all systems can reduce what data is reachable; egress controls can reduce some outbound paths. | **No sandbox in this comparison decides whether information intentionally supplied to the model is appropriate, or controls the provider’s data-handling policy.** A permitted response or tool result can also contain sensitive data. Minimize prompt context and review provider, logging, and retention settings. |
| **Malicious or vulnerable allowed websites, packages, and services** | Codex/Claude proxies, Docker Sandboxes policies, E2B egress rules, and OpenShell request/middleware controls can narrow which destinations and requests are reachable. | **Allowlisting a destination does not make its content trustworthy.** Ordinary Docker has no egress filtering by default; every system can still receive malicious content from allowed sources unless provenance, package, browser, and application checks are added. |
| **Delayed execution of returned or persisted artifacts** | Docker Sandboxes clone mode separates edits until an explicit fetch; E2B and microVM approaches separate guest files from host by default; filesystem policies can protect selected configuration paths. | **None validates that generated code is safe when later run outside the sandbox.** Hooks, CI, package scripts, binaries, and fetched code can become dangerous after transfer or merge. Review artifacts before execution. |
| **Availability, cost, or resource exhaustion** | Ordinary Docker exposes explicit CPU, memory, and process limits; E2B documents resource metrics, plan limits, and timeouts; OpenShell drivers can be configured with resource options. | **The local Codex/Claude command sandboxes and Docker Sandboxes descriptions do not provide the same explicit per-task quota guarantees in these notes.** Limits in any system must be configured and monitored; a microVM alone does not impose a useful cost ceiling. |
| **Persistence of sensitive state** | Docker Sandboxes can be removed with `sbx rm`; E2B provides lifecycle controls and kill operations; container/VM lifecycle controls can discard guest state. | **Persistence is not automatically safe.** E2B pause/resume and snapshots retain state; Docker Sandboxes persist VM state until removal; mounted host files remain after guest cleanup; workspace edits from Codex/Claude persist. Define retention and cleanup explicitly. |
| **Sandbox/runtime vulnerabilities or policy mistakes** | MicroVM boundaries in Docker Sandboxes and E2B, OpenShell’s selectable runtime drivers, and OS enforcement in Codex/Claude provide technical isolation layers. | **No system eliminates implementation vulnerabilities, misconfiguration, or policy bypass.** Ordinary Docker shares the host kernel by design; best-effort filesystem enforcement and permissive exceptions can weaken OpenShell or Claude policies; full-access modes remove key restrictions. Keep runtimes updated and verify effective settings. |
| **Human review mistakes or overbroad approvals** | Approval workflows in Codex and Claude can pause before selected actions; Pi's `pi-permission-modes`/`pi-sandbox` add approval prompts and `pi-ask-permission` adds tool-call review; connector/service approvals may add further checkpoints. | **An approval prompt is not a content-aware safety guarantee.** Pi core's project-trust prompt is not a command approval. Add-ons can remember broad grants or provide bypass/YOLO modes. Broad “allow” settings can authorize damaging actions. Use narrow scopes and enforce limits at the database, OS, or external service. |

In short, the most important risks left outside the sandbox boundary are **the consequences of permitted actions**: writes to shared data, use of authorized identities, actions by separately connected tools, and execution of artifacts after they leave the sandbox. Prevent those with least-privilege credentials, service-side rules, deliberate data sharing, review, backups, and lifecycle controls.

### Destructive database operations

None of these sandbox types should be treated as a SQL safety layer. They can prevent access to a database by denying the network path, socket, or credential, but if the agent can connect as a user with `DROP`, `DELETE`, or administrative privileges, a sandbox typically will not recognize the query as dangerous. Use a dedicated development database, least-privilege database roles, disposable datasets, backups, and service-side safeguards. Approval prompts are useful checkpoints, not a replacement for database authorization.

### Deleting files and changing host settings

Codex and Claude can limit command file access to configured paths, but workspace writes are intentional in their normal editing modes. Ordinary Docker is only as isolated as its mounts, capabilities, and daemon setup. Docker Sandboxes provides a more substantial host boundary through a separate microVM and private Docker Engine; clone or mountless mode avoids live host workspace writes. E2B isolates guest files from the developer host, while OpenShell can restrict paths with Landlock. In every case, explicitly shared paths and files returned to the host remain consequential.

### Network and websites

Command-network policy is not necessarily global network policy. Browsers, app connectors, MCP servers, model service traffic, and host-side integrations can have separate routes. Docker Sandboxes and OpenShell describe default-deny style enforcement; Codex local workspace-write also defaults command networking off; Claude and E2B depend on their configured proxy/egress policy. Ordinary Docker generally needs explicit network isolation or an external egress control. Even a strict allowlist still permits any action at an allowed destination unless additional request-level rules and destination-side authorization prevent it.

### Credentials and LLM requests

There are two distinct questions: what information the agent can read locally, and what information is sent as part of its model context or tool requests. Filesystem isolation can prevent some local reads, but it does not determine what the application intentionally sends to the model provider. Credential brokers (Docker Sandboxes, E2B Secrets, OpenShell providers, and Claude credential masking) can keep raw credential values out of guest processes for supported flows, but they do not make the agent’s use of those credentials harmless. Limit credential scope, keep secrets out of prompts and workspaces, and verify the connected service’s data handling separately.

### External tools and connectors

Treat each integration as its own security boundary. A local command sandbox does not automatically contain an MCP server, browser, plugin, desktop-control surface, or SaaS connector. Docker Sandboxes itself documents that local stdio MCP servers registered with its gateway run on the host. Apply least privilege and approval controls at the integration, and avoid granting broad service accounts just because command execution is sandboxed. Controls differ by where the MCP server runs (inside the sandbox, on the same host, remote): see [MCP servers and sandboxes](mcp-servers-and-sandboxes.md).

## Practical configuration by use case

| Use case | Practical starting controls |
|---|---|
| **Routine local coding** | Keep Codex/Claude filesystem access within the project; for Pi use a least-privilege account or reviewed permission extension and understand project trust is not a sandbox; keep command networking off unless needed; avoid storing production credentials in the workspace; review generated scripts and configuration changes. |
| **Agent with an untrusted prompt or repository** | Prefer whole-process isolation such as Docker Sandboxes clone or mountless mode, OpenShell, or another VM/microVM environment. This is especially important for Pi because untrusted projects may supply extensions/packages and core has no execution sandbox. Restrict egress, disable SSH forwarding and unnecessary host integrations, and inspect fetched changes before running them. |
| **Database work** | Use a disposable development instance and a dedicated database identity with only required privileges. Prefer read-only access for analysis; never rely on shell sandboxing alone to prevent destructive SQL. |
| **Remote user-code execution** | Use an isolated VM/microVM, deny or narrow egress, token-gate ingress, keep platform credentials outside guest environment variables, impose time/concurrency limits, and clean up snapshots and paused sessions. |
| **Central policy and audit needs** | Use OpenShell or an equivalent governed runtime; require filesystem enforcement, inspect effective network/provider policy, scope gateway roles, and export logs to durable storage. |
| **Ordinary Docker build job** | Use a non-root user, minimal mounts/capabilities, no host Docker socket, explicit egress design, resource limits, and pinned inputs. For genuinely untrusted code, prefer a VM boundary. |
